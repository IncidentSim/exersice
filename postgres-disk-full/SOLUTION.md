# Решение инцидента «Новые данные не сохраняются»

## Краткий ответ

Каталог данных PostgreSQL (`/var/lib/postgresql/16/main`) лежит на отдельном небольшом томе, смонтированном в `/var/lib/postgresql` — домашний каталог пользователя `postgres`. Конфигурация резервного копирования `/etc/incidentsim/backup.env` после «релиза» складывает дампы в `~postgres/backups`, то есть на тот же том, и не удаляет старые копии (`BACKUP_KEEP=0`). Таймер `incidentsim-backup.timer` каждые 15 секунд добавляет ещё один дамп, том заполняется, и PostgreSQL не может расширить файлы таблиц.

Исправление — вернуть бэкапы на корневой раздел и включить ротацию, затем удалить накопившиеся дампы с тома данных. Таймер при этом продолжает работать.

## Воспроизведение

```bash
bin/incidentctl incident postgres-disk-full
bin/incidentctl verify postgres-disk-full
```

Проверка падает на первом же замере:

```text
Sample 0: expected HTTP 201 from POST /orders, got 500:
{"error": "database error", "sqlstate": "53100",
 "detail": "could not extend file \"base/16388/16397\": No space left on device ..."}
```

Номера файлов в сообщении зависят от кластера.

## Диагностика

1. Ошибка приходит от базы, а не от приложения. SQLSTATE `53100` — `disk_full`. То же видно в журнале PostgreSQL на корневом разделе:

   ```bash
   tail -n 20 /var/log/postgresql/postgresql-16-main.log
   ```

2. На `/` место есть — это ловушка:

   ```bash
   df -h /
   ```

3. Нужно смотреть файловую систему каталога данных:

   ```bash
   runuser -u postgres -- psql -Atc 'SHOW data_directory'
   df -h /var/lib/postgresql/16/main
   findmnt --target /var/lib/postgresql/16/main
   ```

   `findmnt` показывает отдельный том (`/srv/incidentsim/pgdata.img`, loop, ext4) размером 256 MiB, заполненный на 100%.

4. Что занимает том:

   ```bash
   du -xh --max-depth=1 /var/lib/postgresql | sort -h
   ls -lt /var/lib/postgresql/backups | head
   ```

   Большую часть тома занимают файлы `incidentsim-*.sql` по ~17 MiB в `/var/lib/postgresql/backups`; последний файл обрезан — дамп упал с `No space left on device`.

5. Кто их создаёт и почему они не удаляются:

   ```bash
   systemctl list-timers incidentsim-backup.timer
   systemctl cat incidentsim-backup.service
   cat /etc/incidentsim/backup.env
   journalctl -u incidentsim-backup.service -n 20 --no-pager
   ```

   В `backup.env` указаны `BACKUP_DIR=/var/lib/postgresql/backups` и `BACKUP_KEEP=0`; скрипт `/usr/local/lib/incidentsim/backup.sh` удаляет старые копии только при `BACKUP_KEEP > 0`.

Причина найдена, если показано, что: заполнена именно файловая система каталога данных; место занимают дампы; их без ротации регулярно пишет `incidentsim-backup.timer`. Подтвердить это можно наблюдением: после освобождения места свободное пространство на томе уменьшается примерно на 17 MiB каждые 15 секунд.

## Корневая причина

Резервные копии хранятся на том же томе, что и данные, и без ротации. Одно освобождение места проблему не решает: таймер снова заполняет том примерно за две минуты.

## Исправление вручную

1. Вернуть бэкапы на корневой раздел и включить ротацию. Сначала конфигурация, потом очистка, иначе следующий запуск таймера снова начнёт писать на том:

   ```bash
   cat > /etc/incidentsim/backup.env <<'EOF'
   BACKUP_DATABASE=incidentsim
   BACKUP_DIR=/var/backups/incidentsim
   BACKUP_KEEP=5
   EOF
   install -d -o postgres -g postgres -m 0750 /var/backups/incidentsim
   ```

   Файл окружения читается при каждом запуске сервиса, перезапуск таймера не нужен.

2. Сохранить последний целый дамп и освободить том:

   ```bash
   ls -lt /var/lib/postgresql/backups | head -3
   # скопировать последний полный (не обрезанный) дамп в /var/backups/incidentsim при необходимости
   rm -rf /var/lib/postgresql/backups
   ```

3. Убедиться, что бэкапы создаются в новом месте, а место на томе не убывает:

   ```bash
   systemctl start incidentsim-backup.service
   ls -l /var/backups/incidentsim
   watch -n 5 df -h /var/lib/postgresql
   ```

PostgreSQL перезапускать не нужно: как только место появляется, запись снова работает.

Допустимый вариант — оставить бэкапы на томе, но включить ротацию (`BACKUP_KEEP`). Учтите две вещи. Во-первых, на заполненном томе следующий дамп упадёт раньше, чем дойдёт до ротации, поэтому лишние копии (и обрезанный последний файл) нужно удалить вручную. Во-вторых, проверка требует не меньше 48 MiB свободного места на томе, а одна копия занимает ~17 MiB, так что на томе помещается не больше 4 копий (при `BACKUP_KEEP=3` остаётся ~71 MiB). Проверка проходит, когда число копий уже дошло до лимита и занятое место перестало расти. Держать копии рядом с данными всё равно плохая практика.

## Неправильные исправления

| Действие | Что происходит | Проверка |
|---|---|---|
| Только удалить дампы | За 2 минуты таймер записывает ~8 новых дампов (~136 MiB) и снова заполняет том | падает: место убывает, затем запись снова отклоняется |
| Остановить или отключить таймер | Место больше не убывает, но нарушено условие задачи | падает: нет новых успешных бэкапов |
| Перезапустить PostgreSQL | Кластер поднимается, но место не освобождается | падает: запись по-прежнему отклоняется с `53100` |
| Увеличить том | Только отодвигает момент заполнения | падает: место убывает быстрее допуска |
| Перенести бэкапы на `/`, но оставить `BACKUP_KEEP=0` | Корневой раздел заполняется (~4 GiB в час) и может сломать SSH | проверка этого не ловит — не делайте так |

## Восстановление через исходный код упражнения

```bash
bin/incidentctl infra postgres-disk-full
```

Infra-playbook ставит на паузу таймер, удаляет дампы с тома данных, возвращает `backup.env` (каталог `/var/backups/incidentsim`, хранить 5 копий) и снова запускает таймер.

## Проверка решения

```bash
bin/incidentctl verify postgres-disk-full
```

Проверка длится около двух минут: 13 замеров с интервалом 10 секунд. На каждом замере она:

- сохраняет тестовый заказ через `POST /orders` (заметка 1500 символов, чтобы вставки быстро требовали новых страниц таблицы) и читает его через `GET /orders/<id>`;
- измеряет свободное место на файловой системе каталога данных, который сообщает сам PostgreSQL (`SHOW data_directory`);
- читает результат последнего запуска `incidentsim-backup.service` (`systemctl show`).

После окна проверка требует:

- все записи и чтения успешны;
- свободное место на томе данных не меньше 48 MiB и упало не больше чем на 40 MiB от первого замера (один дамп — ~17 MiB);
- не меньше 5 успешных запусков бэкапа за окно (ожидается ~8).

Ожидаемый результат:

```text
8 backups finished successfully during the window.
Free space on the data filesystem stayed between 120 and 120 MiB.
```

Значения измерены на ВМ Ubuntu 24.04.5, 1 vCPU, 1 GiB (Lima, Apple Virtualization.framework); на другой ВМ они могут немного отличаться.

## Параметры калибровки

| Параметр | Значение |
|---|---|
| Том данных | 256 MiB, ext4 без резерва root (`-m 0`); доступно 224 MiB |
| Занято PostgreSQL после infra | 97 MiB (кластер, база, `max_wal_size = 64MB`) |
| Свободно на томе после infra | 120–122 MiB |
| `order_history` | 120 000 строк, дамп 17,2 MiB |
| Период таймера | 15 с (`OnUnitActiveSec`) |
| Скорость заполнения без ротации | ~68 MiB/мин; если только удалить дампы, том снова полон через ~2 мин (120 → 0 MiB за окно проверки) |
| Заполнение тома инцидентом | ~4 с: 7 полных дампов и 1 обрезанный |
| Минимум свободного места после infra | 80 MiB (проверяется infra-playbook) |
