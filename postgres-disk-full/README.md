# Инцидент «Новые данные не сохраняются»

## Ситуация

Сервис заказов `orders-api` принимает заказы по HTTP и хранит их в PostgreSQL. Сервис запущен и отвечает на запросы, но новые заказы перестали сохраняться: `POST /orders` возвращает HTTP 500.

```bash
curl --silent --request POST \
  --header 'Content-Type: application/json' \
  --data '{"item":"book","note":"gift"}' \
  http://127.0.0.1:8080/orders
```

Дежурный уже проверил сервер: процессы запущены, на корневом разделе свободно много места.

## Топология

```text
клиент → orders-api 127.0.0.1:8080 → PostgreSQL 16 (Unix-сокет, база incidentsim)
```

- `incidentsim-orders-api.service` — HTTP-сервис: `GET /healthz`, `POST /orders`, `GET /orders/<id>`.
- `postgresql@16-main.service` — кластер PostgreSQL.
- `incidentsim-backup.timer` — логическое резервное копирование базы каждые 15 секунд.

## Задача

Найдите причину, по которой база не может сохранить новые данные, и устраните её так, чтобы проблема не вернулась.

Ограничения:

- резервное копирование — требование службы эксплуатации: его нельзя отключать, останавливать или запускать реже;
- контракт `orders-api` менять нельзя;
- данные заказов терять нельзя.

## Критерий готовности

```bash
bin/incidentctl verify postgres-disk-full
```

Проверка в течение двух минут наблюдает за сервисом: каждые 10 секунд сохраняет и читает тестовый заказ через `orders-api`, следит за свободным местом в хранилище PostgreSQL и за тем, что резервные копии продолжают успешно создаваться. Разовое улучшение, которое исчезает за это время, не засчитывается.

## Управление сценарием

```bash
bin/incidentctl infra postgres-disk-full
bin/incidentctl incident postgres-disk-full
bin/incidentctl verify postgres-disk-full
```

После `incident` проверка должна падать, пока проблема не устранена.
